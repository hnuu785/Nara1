# 추가 라벨링 실행 명세 초안

## 목표와 역할
- 목표는 공식 평가 Macro F1 0.90. 파일럿의 용도는 라벨 품질과 판정 명세 검증이며 달성 예측이 아니다.
- OpenAI API는 대회 제공 자료의 자가 라벨 생성에만 사용한다. 웹 검색과 외부 문서 검색 도구를 연결하지 않는다.
- 최종 제출은 고정 Gemma와 허용된 정적 자산·규칙으로 실행한다. 추가 가중치를 학습하지 않는다.
- 본 문서는 설계만 정의한다. API 호출, 유료 요청, 원본 코드 수정은 수행하지 않았다.

## 순서
1. 담당자가 1차 12개 판정 경계를 검토한다. 답변을 일반화한 항목별 명세에 반영한다.
2. OpenAI의 가용 모델을 확인하고, dev 200건의 공식 정답을 프롬프트에서 숨긴 상태로 라벨 생성 품질을 측정한다. 이미 분석한 dev이므로 독립 테스트라고 주장하지 않는다.
3. 무라벨 20,000건에서 300건 파일럿을 선정한다. 무작위 100건과 취약·경계 사례 200건을 구분해 기록한다. 공백을 제거한 전체 문서 기준 exact duplicate는 26개 추가 중복이 있으며, 유사 문서도 같은 그룹으로 묶어 개발·검증 간 분리한다.
4. 300건은 라벨링 명세 개선용이다. 이후 독립 검증 세트를 별도 표본에서 선정·고정한다.
5. 1차 판정과 검토 요청은 별도 API 요청으로 수행한다. 독립 검토자는 1차 결과를 처음부터 보지 않고 판정한 다음 불일치를 비교한다. 가능한 경우 다른 OpenAI 모델을 쓰되, 같은 계열 모델 오류가 상관될 수 있음을 고려한다.
6. 불일치·법령 적용 불명확·자료 부족은 담당자 검토로 보낸다. 합의 사례도 무작위 표본을 사람이 검토한다. 모든 불일치를 억지 0/1로 확정하지 않는다.
7. 통과한 항목부터 추가 라벨을 확대한다. 항목별 양성·헷갈리는 음성의 확보 수와 사람 검토 결과를 함께 보고한다.

## 출력 필드
공고 id, 항목, 적용 여부, 판정(0/1/보류), 추출 사실, 문서 id와 원문 구간, 배포 법령 위치, 예외 적용, 자료 부족 사유, 검토 상태를 저장한다. 부재 탐지에는 검토한 문서 범위를 기록한다. 최종 제출용 근거와 내부 검토용 근거는 구분한다.

## 품질 점검
- JSON 스키마 준수와 의미 정확도는 별개다. Structured Outputs는 형식에만 사용한다.
- 정답과 ID 정렬을 검증하고 항목별 TP/FP/FN/F1을 계산한다. 보류율은 별도로 보고한다.
- 원문 인용이 실제 해당 공고에 포함되는지 검사한다. 경쟁제품 판단에는 제공 품목표의 조건까지 확인한다.
- 모델 간 합의율을 정확도로 표기하지 않는다. 사람 검토에서도 공식 예시와의 불일치 원인을 기록한다.
- 요청 id, 실제 모델 식별자, 프롬프트·명세 버전, 입력 해시, 원응답, 토큰 사용량, 생성 시각, 검토 이력을 보존한다.

## 실행 방식
초기 파일럿은 결과를 빠르게 확인할 수 있는 일반 Responses API 요청으로 계획한다. 계정의 모델별 RPM/TPM을 확인한 뒤 동시 실행 수를 정한다. Batch는 24시간 완료 창을 사용하므로 마감 직전의 필수 경로에는 넣지 않는다. API 키는 환경변수에 두고 자료·로그·채팅에 기록하지 않는다. 계정의 실제 모델 접근권한과 한도는 아직 확인하지 않았다.
